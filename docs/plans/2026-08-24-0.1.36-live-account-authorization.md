# Desktop 0.1.36 Live Account Authorization Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Add real-account authorization and redacted end-to-end verification for GitHub, Feishu/Lark, GitLab, and DingTalk without moving credentials into the renderer or replacing DeepSeek Harness's official MCP bridge.

**Architecture:** Keep connector execution on the existing `@deepseek-ai/dsh-mcp-client` profile path. Add a desktop-main-process authorization layer with provider adapters, encrypted credential storage, OAuth discovery/PKCE support, and one renderer-safe state model. GitHub and GitLab use remote MCP authorization where supported; Feishu uses the official `lark-mcp` login/logout/OAuth path; DingTalk uses official application credentials and permission profiles.

**Tech Stack:** Electron 43, Node.js ESM, React 18, TypeScript, Vitest, Node test runner, Electron `safeStorage`, loopback OAuth callback, MCP remote HTTP, pnpm workspace.

---

## Scope and hard boundaries

1. This release covers GitHub, Feishu/Lark, GitLab, and DingTalk only.
2. OAuth tokens, refresh tokens, PATs, App Secrets, authorization codes, and provider responses containing credentials stay in the Electron main process.
3. The renderer receives only state such as `ready`, `expired`, `missing-permission`, or `reauthorization-required`.
4. OAuth uses browser authorization, PKCE S256, a cryptographically random `state`, and a loopback callback bound to `127.0.0.1` on an ephemeral port.
5. Do not hardcode authorization/token endpoints when MCP protected-resource or OAuth authorization-server metadata can be discovered.
6. GitHub offers OAuth first and a fine-grained PAT fallback. GitLab uses OAuth Dynamic Client Registration when the instance permits it, with an optional pre-registered public client ID.
7. Feishu must use the official `@larksuiteoapi/lark-mcp` login/logout or `mcp --oauth` behavior. Do not implement a parallel proprietary token exchange unless the official CLI cannot expose the required lifecycle.
8. DingTalk is application authorization, not user OAuth. Require Client ID, Client Secret, selected official profiles, and a permission-readiness checklist.
9. Real-account checks are manual protected tests. CI uses deterministic provider simulators and never receives personal production credentials.
10. A provider is not labeled “live verified” until the redacted evidence matrix passes on a disposable or least-privilege account.

## Definition of done

- A user can authorize, inspect status, and disconnect each of the four providers from the connector center.
- GitHub and GitLab complete browser authorization or present a precise fallback/ineligibility message.
- Feishu completes official CLI login and a read-only tool call; logout removes the local authorization.
- DingTalk validates credentials, selected profiles, and at least one read-only tool from an enabled profile.
- No credential-shaped value appears in `connectors.json`, generated Cordis patches, logs, diagnostics, snapshots, screenshots, or exported support bundles.
- macOS arm64, macOS x64, and Windows x64 deterministic tests pass.
- Live evidence records provider, auth mode, platform, test operation, timestamp, and result, but never account IDs or secrets.
