# Desktop 0.1.38 Connector Lifecycle and Store Tiers Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Make expired, revoked, and disconnected connector credentials recoverable, and present a trustworthy connector store with verified, community, and experimental tiers.

**Architecture:** Add one provider-neutral authorization lifecycle state machine above the 0.1.36 adapters and 0.1.37 official Skill installers. Keep secret values in the existing encrypted store while persisting only safe expiry, retry, and verification metadata. Convert the current static catalog into a validated built-in store manifest; remote community ingestion remains out of scope until signing and review infrastructure exists.

**Tech Stack:** Electron main process, Node.js ESM, React/TypeScript, Vitest, Node test runner, encrypted secret storage, provider adapters, static catalog manifest, pnpm workspace.

---

## Scope and hard boundaries

1. “Disable”, “Disconnect authorization”, “Remove”, and “Reconnect” are distinct actions.
2. Disable preserves configuration and credentials but stops profile registration.
3. Disconnect revokes or deletes app-owned authorization while preserving connector configuration.
4. Remove deletes configuration and app-owned credentials after confirmation.
5. Reconnect replaces credentials atomically and never leaves a half-authorized connector active.
6. Refresh happens only for providers that issued a refresh token or documented a supported refresh mechanism.
7. A 401 is not automatically “expired”; classify invalid, revoked, missing, and provider-unavailable when evidence permits.
8. Automatic retries use bounded exponential backoff with jitter and never loop on authorization failures.
9. Store tiers describe evidence, not absolute safety. “Verified” means source, automated tests, and a dated live matrix passed.
10. 0.1.38 ships a built-in reviewed manifest. Downloading/installing arbitrary remote community code is out of scope.

## Store tier definitions

| Tier | Required evidence | Default action |
| --- | --- | --- |
| Verified | Provider/official source, deterministic tests, live auth/tool matrix, platform matrix, reviewed permissions | Normal install/connect flow |
| Community | Public source, license and provenance recorded, deterministic parser/package tests, no official endorsement | Extra source/permission confirmation |
| Experimental | Incomplete official path, unstable API, missing live verification, or unsupported lifecycle | Hidden behind experimental filter and warning |

Every entry also records `lastVerifiedAt`, `verifiedVersion`, `platforms`, `authModes`, `capabilities`, `permissionSummary`, `sourceUrl`, and `knownLimitations`.

## Definition of done

- Expired tokens refresh once or move to a clear reauthorization state.
- Provider-side revocation is detected and surfaced without leaking the response.
- Disconnect and reconnect work for all live-verified 0.1.36/0.1.37 integrations.
- Concurrent tool calls do not create refresh storms.
- Installed connector cards expose status, next action, last healthy time, and last failure category.
- The store supports search/filter by tier, provider, capability, auth mode, platform, and installed state.
- Tier labels are derived from validated manifest data, not UI hardcoding.
- All three desktop platforms pass deterministic lifecycle and catalog tests.

  tier: ConnectorTier
  sourceUrl: string
  license?: string
  lastVerifiedAt?: string

- unique IDs;
- HTTPS provider/source URLs;
- verified entries require dated live evidence, all platform declarations, and a version;
- community entries require a public source and license;
- experimental entries cannot claim live verification;
- executable stdio entries require local execution disclosure;
- official/provider source and tier are independent fields.
