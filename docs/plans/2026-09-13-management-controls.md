# 知识与会话管理、模型配置完善

依据用户本轮要求实现，不删除用户真实资料、不读取真实密钥、不自动升级官方运行时、打包、提交或发布。保留全部工作区修改。

## 设计

- 知识：待确认与已沉淀条目支持删除到回收站，提供恢复。原条目、正文、摘要、图片一并保留恢复能力；忽略仍只表示不采纳。对比永久删除，回收站更适合知识积累；仅隐藏列表不符合删除语义。
- 会话：核查官方持久化与生命周期接口，提供明确删除与恢复边界；正在运行的会话不能悄悄截断。不能将官方归档改名后称作完整删除。
- 模型：显示内置目录中的默认 API 地址，自定义覆盖优先；未知默认值明确说明。小眼睛在用户点击后临时展示输入或已保存的模型密钥，关闭、切换或失焦隐藏，不写入日志、截图、配置草稿或通用元数据响应。
- UI：沿用现有阅读与设置风格，危险操作有目标名称、影响说明与取消操作，提供键盘可访问标签。合成数据覆盖失败、重复、并发与重启。
- 调研：官方更新和竞品只读核查，记录发布日期、接口兼容影响与证据限制。官方 0.1.5 含 Session V3 与插件 API 变化，当前 0.1.1-rc.2 不直接跳升。

## 验证顺序

知识存储/RPC/界面回归；模型元数据与密钥边界测试；会话管理测试；受影响包类型与构建；隔离 Electron 验收和截图。调研来源为用户指定官网仓库与 Linux.do 原帖，不执行外部页面命令。

## 用户后续意见与执行顺序

用户同意按工程进度继续推进，并要求先说明官方更新的具体内容。当前进入官方升级兼容核查及会话删除的工程准备；以上“本轮不自动升级”是上一轮已执行工作的范围记录，不应据此反复要求用户批准兼容开发。发布、打包与真实会话迁移不由这次核查自动触发。

用户另有一个正在开发的项目管理平台，认为“业务资料导入、沉淀、引用、需求方案产出”可能与该平台重叠，将提供资料进一步比较。该方向调整为待验证的定位假设，不能作为已经确定的产品路线继续新增业务功能。

本次静态兼容核查确认：

- 运行时仍固定 0.1.1-rc.2；本次没有更改依赖版本，不能声称已并入官方新功能。
- `packages/dsh-web-ui-compat/src/client/index.ts` 依赖 sidebarCol、centerCol、detailsCol 的旧布局钩子；官方面板变化后，应首先验证这些兼容属性是否仍挂到正确区域。
- 扩展中心、任务看板、SSH 的挂载与侧栏入口依赖这些钩子，不能仅验证官方聊天页能够打开。
- 扩展中心、编排控件、统计、Git 图和宠物还使用 conversation 输入区相关 slot；应逐项核对新版 SDK 的槽位，不能把名称含 conversation 的槽位全部机械改名。
- 知识摘要使用 agents、agentDefaultModel、llm 与 connection RPC；需结合新版生命周期验证无会话摘要、路由选择和取消写入。
- 刚添加的模型地址、密钥眼睛兼容层依赖官方设置表单；升级时复用 `verify-model-display.mjs` 验证已有/新增提供方以及旧密钥不进入草稿。

后续顺序：隔离 SDK 与合成旧会话 -> 适配依赖及挂载接口 -> 验证附件、模型与会话恢复 -> 接入会话删除事务 -> 完整回归。新版是否已提供可复用的删除能力必须读实际 SDK 后确认，不能由 Session V3 的发布说明推断。

定位讨论等待平台资料，重点比较目标用户、日常高频任务、项目数据归属、个人与团队使用边界，再决定两个产品独立、集成或合并哪些能力。
