# 管理功能与上游、竞品核查

核查日期：2026-09-13。保留原工作区修改，本轮未升级 SDK、提交、发布或重新打包 DMG。功能验证只使用临时合成文章和合成密钥，没有读取真实凭证文件或删除真实资料。

## 本轮实现

### 知识删除与恢复

待确认、已沉淀卡片均新增删除操作。确认框写明目标标题及回收站影响；取消不写入。条目以原子重命名移出活动 items 集合，原文与配图资源保留；回收站只提供恢复，不提供阅读、编辑、AI 整理等活动条目操作。恢复到原状态，不能把候选自动变成已沉淀。

删除与条目更新使用相同的进程内锁；删除校验 updatedAt，拒绝过期请求、取消请求和目标冲突。相同导入 requestId 的迟到重试不能重新创建已删除条目。普通列表和 detail 不返回回收站条目。存储测试通过重新创建 Store 实例验证重启后的恢复与图片完整性。

这里是可恢复删除，不是永久擦除，也不清除历史对话中已经引用过的内容。当前没有自动清空回收站策略；本轮没有新增跨进程协调机制。

### 模型地址与密钥

预设地址来自当前安装的官方 SDK 所依赖的 pi-ai 目录，不手写厂商地址表；DeepSeek 独立适配器采用其官方默认值。SDK 只导出 ESM 的目录入口，因此按依赖包声明的 import 导出路径加载，未改动 node_modules。

选中 xiaomi-token-plan-ams 时，目录默认值为：

`https://token-plan-ams.xiaomimimo.com/v1`

默认地址直接显示在密钥框下方，即使高级设置折叠也可见。自定义 URL 优先显示；新增自定义提供方的 example 占位地址不能被误当成默认地址。选用中转服务仍应填写中转服务的 URL。

眼睛位于密钥框右侧。新输入只切换 input 类型；查看已保存密钥只在点击后通过受限桌面 IPC 请求当前提供方的本地模型引用。旧密钥出现在独立只读临时字段，不写回 React 草稿，不因点击保存而替换密钥。失焦、页面隐藏、切换提供方、移除编辑器、保存/取消和 30 秒超时都会隐藏并清空临时字段，迟到响应不能重新展示。

IPC 校验主窗口、顶层 frame、运行时 origin，并在异步读取后复核。请求只能含 providerId，不能传任意路径或凭证引用；响应不枚举其他密钥。凭证文件拒绝符号链接、过大文件和宽松权限，解析错误统一返回固定错误码。

支持模型设置页保存在本地凭证 refs 中的 API key；环境覆盖不会被误展示为磁盘旧值，OAuth 授权不是可展示的 API key。环境密钥、其他插件凭证和 OAuth grants 不在本次读取范围。

## 未完成：历史会话删除

当前 0.1.1-rc.2 SDK 的 workspace API 只有 archiveSession；SessionPersistence 暴露 locate/load/append 等能力，没有删除事务。locate 的 SDK 注释明确说明位置提示不是授权令牌。AgentHandle.dispose 是创建者持有的生命周期能力；通过 agents.get 获取的 Agent 不附带该 disposer。

因此不能通过重命名“归档”满足删除，也不能趁会话仍被持久化协调器或活动 Agent 持有时删除 JSONL。全局停止运行时再移动目录会波及其他对话、后台任务和终端，超出对单条历史会话删除的正常预期。本轮没有加入这样的隐式全局中断。

后续实现需要专门的会话删除事务：获取目标生命周期所有权、阻止并发 resume/append、处理分支和子任务引用、刷盘并卸载、移动独立日志和附件至回收站、更新列表/缓存、支持恢复与重启验证。应先在隔离 SDK 适配分支验证生命周期接入，不能声称升级后自动具备删除功能。

## 与 PI-Desktop 的对比

资料：[GitHub README](https://github.com/vastsa/pi-desktop)、[Linux.do 作者原帖](https://linux.do/t/topic/2869113)。本轮阅读公开说明和发布资料，没有安装运行 PI-Desktop，也没有审计其全部源码。以下能力属于文档披露，稳定性不能当作已经实测。

| 维度 | PI-Desktop 的公开设计 | JIWEI 当前判断 |
| --- | --- | --- |
| 主要用户 | 开发者的本地 AI 编程工作台 | 产品经理及低门槛 Agent 用户，定位应继续收敛 |
| 工程分层 | Electron/React、Rust Host Core、pi Agent Sidecar | 官方 Harness SDK 加桌面和插件扩展，复用多，但上游兼容影响明显 |
| 会话与代码工作流 | 搜索、分支、归档、导入会话、队列、diff/review、Agent/Plan/Goal | 功能基础已有，管理闭环和入口一致性仍需补齐 |
| 扩展 | .piplug 市场、MCP、Skills、pi 扩展、工作区面板和服务 | 连接器和 Skills 已有，但完整生态与插件产品化不足 |
| 凭证和数据 | 文档称 OS keychain、JSONL 日志加 SQLite 索引，无强制中转账号 | 模型凭证沿用当前官方本地文件实现；连接器另有桌面安全存储，不应统称所有凭证均在系统钥匙串 |
| 知识工作流 | 本轮公开资料不足以判断其同类文章知识能力 | 公众号导入、原文/摘要/笔记、标签、确认沉淀是值得做深的方向，跨任务复用价值仍待验证 |
| 发布成熟度 | Early Preview 0.14.x，覆盖 macOS/Windows/Linux；作者仍列出升级回退、恢复、沙箱和 E2E 等待办 | 当前侧重 macOS 验证，DMG 为 ad-hoc 签名，仍不是成熟稳定发行 |

我的判断：PI-Desktop 在开发者工作台的范围与管理完整度上更领先，尤其值得学习模型配置、会话组织、插件边界和统一操作反馈。功能数、提交数与 stars 不能证明故障率更低；其 README 也明确插件属于可信代码，尚非完整操作系统沙箱。

JIWEI 应优先形成“接入业务资料 -> 可靠阅读整理 -> 用户确认 -> 在新任务中检索引用 -> 产出需求/方案”的可验证闭环。比继续堆 IDE 功能更有针对性。下一阶段建议先补会话管理与 SDK 适配，再做知识引用、来源追溯和少量产品经理任务模板。

后续定位修正：用户指出上述方向可能与其正在开发的项目管理平台重叠，将提供该平台资料。上述建议因此只保留为待验证假设，暂不据此新增产品经理业务流程或项目管理能力。先评估两个产品的用户、核心任务和数据归属；通用工程完善继续推进。

PI-Desktop 为 LGPL-3.0 项目；本轮只借鉴公开交互与架构思路，没有复制其代码。
